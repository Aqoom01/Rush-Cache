# split-comparison 결과

2026-10-22 실행, `summary.csv`. 조건은 [README.md](README.md). seed 10개의 평균과 범위다.

## 요약

부하를 보고 자르는 `split-for-heat`는 요청이 한쪽에 몰린 Tablet(S2)을 다음 window에서도 0.509로 거의 반반 나눴다. 가운데에서 자르는 `midpoint-split`은 0.875로 한쪽에 몰렸다. key 하나가 90%를 받는 Tablet(S3)에서는 `midpoint-split`이 10번 모두 효과 없이 분할했고(0.952), `split-for-heat`는 10번 모두 `SINGLE_HOT_KEY`로 보류했다.

## θ = 0.8 (기본값)

| 시나리오 | variant | 분할 | 보류 (`SINGLE_HOT_KEY`) | 다음 window 큰 쪽 비율 평균 (최소-최대) | 효과 없는 분할 |
|---|---|---|---|---|---|
| S1 균등 | `midpoint-split` | 10/10 | 0 | 0.514 (0.501-0.539) | 0/10 |
| S1 균등 | `split-for-heat` | 10/10 | 0 | 0.509 (0.502-0.522) | 0/10 |
| S2 Hot Range | `midpoint-split` | 10/10 | 0 | 0.875 (0.863-0.890) | 10/10 |
| S2 Hot Range | `split-for-heat` | 10/10 | 0 | 0.509 (0.501-0.526) | 0/10 |
| S3 단일 Hot Key | `midpoint-split` | 10/10 | 0 | 0.952 (0.948-0.959) | 10/10 |
| S3 단일 Hot Key | `split-for-heat` | 0/10 | 10/10 | - | - |

- **S1:** 두 정책이 비슷하다. `midpoint-split`이 조금 더 벌어진 것(0.514)은 난수 key가 2^63 양쪽에 정확히 500개씩 나뉘지 않기 때문이다. `split-for-heat`는 실제 요청을 보고 자르므로 그 차이가 없다.
- **S2:** `midpoint-split`의 0.875는 설계 문서의 예상값과 같다. 2^63 왼쪽에 뜨거운 key 200개(80%)와 차가운 key 약 300개(약 7.5%)가 함께 들어가기 때문이다. `split-for-heat`는 결정에 쓴 window가 아닌 **다음 window에서도** 0.509를 유지했다. 분할 효과가 관찰 window에만 맞춘 결과가 아니라는 뜻이다.
- **S3:** 어떤 분할도 뜨거운 key 하나를 나누지 못한다(`hottest_key_share` 약 0.9). `midpoint-split`의 분할은 데이터 이동 비용만 들고 부하는 줄이지 못한다. `split-for-heat`는 이를 감지해 보류했다.

## θ 민감도 (0.6, 0.7, 0.8, 0.9)

`split-for-heat`의 결정은 네 θ 모두에서 같았다(S1·S2 분할, S3 보류). 달라진 것은 `midpoint-split`의 "효과 없는 분할" 판정 하나뿐이다. S2에서 θ = 0.9일 때 0.875가 기준 아래라 0/10이 됐다.

**이 결과는 "θ가 영향이 없다"가 아니라 "이 시나리오로는 θ의 영향을 볼 수 없다"는 뜻이다.** S2는 반반에 가깝게 잘려 어떤 θ보다도 낮고, S3는 가장 잘 잘라도 (1 + 0.9) / 2 ≈ 0.95라 어떤 θ보다도 높다. θ가 결정을 가르는 것은 뜨거운 key 하나의 비율 s가 2θ - 1 근처일 때다(θ = 0.6-0.9이면 s = 20-80%). θ 민감도를 보려면 s를 그 범위에서 바꾸는 시나리오를 추가해야 한다.

## 한계

- Tablet 하나, 분할 한 번만 본다. 연쇄 분할과 분할 후 유예(§4.1)는 다루지 않았다.
- 요청 분포가 window 사이에 바뀌지 않는다. 뜨거운 구간이 이동하는 부하에서는 "다음 window" 효과가 달라질 수 있다.
- 실제 서버·노드·데이터 이동이 없다. 분할 후 p99 latency나 처리량은 B1 `hash-range-tablet`과 B3 이동이 구현된 뒤 측정한다.
- S2의 "앞쪽 20%"는 해시값 순서 기준이다. 실제 key 이름이 비슷한 것끼리 뜨거워지는 경우는 hash로 흩어지므로 이 모양이 되지 않는다.
