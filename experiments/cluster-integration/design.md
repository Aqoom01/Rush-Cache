# B1·B2·B3 통합 클러스터 실험 설계

실서버(EC2)에서 라우팅(B1)·균형(B2)·이동(B3)을 연동해 측정한다. 작성 2026-11-09 (B3 검토 반영 개정), 담당 B1(홍진규). E3는 B2(서현), E4~E6은 B3(현호)와 분담한다. 최종발표 11/18 기준으로 우선순위를 정했다.

## 1. 원칙

**실서버에서는 시뮬레이션으로 못 재는 것만 잰다.** 방법론별 균형·이동량 수치는 각 파트 시뮬레이션(experiments/)으로 확보했고, 네트워크에 올려도 그 숫자는 바뀌지 않는다. 실서버에서만 나오는 것:

- 실제 지연·처리량 (라우팅 판정, MOVED 왕복의 비용)
- 라우팅 표 전파와 낡은 표의 대가
- 이동 **중**의 서비스 영향 (freeze, miss·BUSY, p99 스파이크)
- 실제 NIC 대역에서의 이동 경쟁과 scale-out/in의 끝에서 끝 시간

방법론 전체 교차가 아니라 **기본 조합을 고정하고 실험마다 한 축만 바꾼다.**

- 고정 기본 조합: B1 해시범위 Tablet(split 가능한 본안) + B2 heat-split(θ0.8) + **B3 pre-copy**(B3 선정 기본 방식, [근거](../b3-live-migration/results.md))
- **wire 완성 전 단계(E1~E3)는 데이터 복사 없는 cutover만 쓴다.** 이때도 commit 후 source 범위 삭제(cleanup)는 적용한다 — 같은 Tablet이 원래 노드로 돌아올 때 옛 값이 되살아나는 stale HIT를 막는다. 서버 cutover 경로에 cleanup이 있는지 확인 항목(§5).
- B3 수치 인용은 experiments/b3-live-migration/의 **현재** 결과 문서를 따른다. 삭제된 이전 run(855회 Scheduler 등)의 수치를 쓰지 않는다.

## 2. 환경과 제약

infra/README.md의 클러스터를 그대로 쓴다.

| 항목 | 값 |
|---|---|
| 인스턴스 | m6gd.medium (**1 vCPU**, 4 GiB, arm64, Graviton2) 고정 — 교보재 조건. 서버·러너 모두 코어 1개라 스레드 경합이 측정에 포함된다(A1 실측도 같은 조건) |
| 구성 | cache-server 1~8대 + 부하 생성 1대 (합계 9대 이하) |
| 서버 | `B1ServerMain` (node 0 = Controller 겸임), 초기 표는 모든 노드가 같은 설정으로 계산 |
| 실행 | GitLab CI 수동 트리거: up → run → S3 업로드 → down. 이것이 **런(run)** 1회 |
| 결과 | S3 결과 버킷 (실패해도 업로드) |

**런 = 클러스터를 한 번 띄웠다 내리는 것.** 노드 수를 바꾸면 런이 바뀐다. 같은 노드 수의 조건(정책·부하 수준)은 **상태 리셋 절차(§3)를 거쳐 한 런 안에서 순차 실행**해 런 수와 편차를 줄인다.

### 측정 환경 기록 (매 런 공통)

- **이동 대역 실측:** 런 시작 시 노드 간 iperf3를 돌려 기록한다. 소형 인스턴스의 "최대 N Gbps"는 버스트 수치일 수 있으므로 `aws ec2 describe-instance-types`의 기준 대역도 함께 적는다.
- **EC2 준비 지연:** 인스턴스 생성 → 서버 READY까지를 CI 로그 타임스탬프로 기록한다. B3 시뮬레이션의 준비 지연 파라미터에 실측값을 준다. 추가 런 불필요.
- **서버 관측:** 노드 CPU(sar)·GC 로그를 남겨 p99 스파이크의 원인(이동 vs GC)을 분리한다. 이벤트 타임라인은 러너 시계 기준으로 찍는다.
- **메모리:** key 100만 × value 1 KiB + JVM 오버헤드가 4 GiB 안에 드는지 단일 노드 런에서 힙 설정을 확인한다.

### 부하 생성기 1대 제한

부하 생성기도 1 vCPU 1대뿐이라 서버 8대는커녕 1대도 포화 근처에서는 생성기 자신이 병목이 될 수 있다. 처리량 포화 비교 대신 **고정 RPS에서 지연을 비교**하고, RPS 단계는 낮게 시작해 부하 노드 CPU가 여유 있는 구간(예: 70% 이하)만 유효한 비교로 인정한다. 모든 런에서 부하 노드 CPU를 기록해 증빙한다.

### 지연 측정은 open-loop

고정 RPS는 요청을 **예정 시각에** 보내고 지연을 예정 시각부터 잰다(coordinated omission 방지). 응답을 기다렸다 보내는 closed-loop면 freeze 구간의 p99가 과소 측정되어 E4 비교가 무력해진다.

### 반복

조건당 런을 늘리는 대신 **런 안에서 warm-up 제외 측정 구간 3회 반복**, 반복 전 상태 리셋. 평균·최소·최대를 기록한다.

## 3. 공통 조건과 러너 요구사항

| 항목 | 값 |
|---|---|
| key | 100만 개, value 1 KiB (시뮬레이션은 128 B — 차이를 결과에 명시, §7) |
| 부하 구성 | 기본 SET/GET/DELETE, **DELETE 30%**(B3 시뮬레이션과 동일, stale HIT 검사에 필요) |
| 쏠림 부하 | Zipf θ0.99 (B1 시뮬레이션과 동일) |
| 표 변경 트리거 | 러너가 CONTROL(opcode 8)로 controller에 지시 — A1의 신뢰 master 패턴 |

**러너(멀티노드 클라이언트) 요구사항** — 선행 작업 2(§5):

- 표를 들고 직행, MOVED 시 §6-1 redirect 추적(최대 3회), 요청별 **hop 수 태깅**
- **BUSY 재시도 규칙**(최대 횟수·간격을 config로): post-copy는 미도착 key를 BUSY로 응답한다(MISS가 아니다). BUSY 비율과 재시도 포함 지연을 별도 지표로 남긴다
- 노드별 요청 집계는 **최종 도착 노드**(redirect 따라간 결과) 기준
- 이동 이벤트(CONTROL 전송·완료 시각) 기록 — 타임라인 대조용
- **정합성 기록:** 성공 응답을 oracle로 보관
- **상태 리셋:** 측정 반복·조건 전환 전에 표를 초기 상태로 되돌리고(CONTROL move로 원복) 데이터를 다시 적재하는 절차

**정합성 검사 (전 실험 공통, 특히 E2~E6):** 러너 oracle과 이동 후 값을 key 단위로 대조한다. 서버 수정 없이 가능하다.

- 성공한 SET이 이동 후 사라진 건수 = 0
- 성공한 DELETE 이후 값이 다시 보이는 stale HIT = 0
- commit 후 옛 주인이 받아들인 쓰기(표 push 도착 전 틈, fencing) = 0

## 4. 실험 목록

| 실험 | 비교하는 방법론 | B1 | B2 | B3 | 런 |
|---|---|---|---|---|---|
| E1 라우팅 오버헤드 | (비교 없음 — 기반 측정) | 측정 대상 | — | — | 4 |
| E2 MOVED·표 전파 | hop 0 vs hop 1 | 측정 대상 | — | — | 1 |
| E3 쏠림 복구 | B2 split 정책 3종 | 도구 | **측정 대상** | cutover+cleanup | 1~3 |
| E4 이동 방식 | **stop-and-copy vs pre-copy** × 쓰기율 2단계 | 도구 | — | **측정 대상** | 2 |
| E5+E6 다중 이동·scale-in | B3 스케줄러 2~3종 (drain 기반) | 도구 | — | **측정 대상** | 2~3 |
| (여유 시) scale-out / source kill / post-copy / SLAMIG | | | | | +1~3 |

핵심 약 10런(런당 ~20분, EC2 3~4시간) + 여유 시 추가. E1·E2 = B1 단독, E3 = B1+B2, E4~E6 = B1+B3.

### E1. 라우팅 오버헤드

- **질문:** 라우팅 층(소유권 판정·표 유지·분산)의 오버헤드는 얼마인가. ("스케일 확인"이 아니다 — 고정 RPS에서 노드를 늘리면 노드당 부하만 줄어 스케일을 보여주지 못한다.)
- **방법:** RPS를 2~3단계로 올려 가며(런 내 순차) 노드 1(기존 단일 노드 서버, 라우팅 없음)·1(B1)·4·8 구성의 지연을 잰다. 클라이언트는 표를 알고 직행.
- **지표:** RPS 단계별 p50/p99, 달성 RPS, 부하 노드 CPU.
- **런 4:** baseline 1대 / B1 1대 / 4대 / 8대.

### E2. MOVED 비용과 표 전파

- **질문:** 낡은 표의 대가(hop 1회 추가 왕복)와 표 변경의 전파 품질.
- **방법:** 8대 1런. 부하를 유지하며 CONTROL로 이동 20건 연속 실행. 요청별 hop 수를 태깅해 **같은 런에서 hop 0 vs hop 1 지연을 비교**한다(초기 표 고정 클라를 따로 두는 방식은 선행 이동이 없으면 MOVED가 안 나므로 쓰지 않는다).
- **지표:** hop 0 vs 1 지연 차이, **이동 1건당 MOVED 수**(정규화), hop ≥ 2(노드 간 표 불일치)와 3회 초과 실패 건수(별도 집계), 정합성 3종(특히 fencing).
- 수렴 "시간"은 push가 밀리초 단위라 폴링 해상도 이하 — 주 지표로 쓰지 않는다.
- **런 1.**

### E3. 쏠림 복구 — B2 split 정책 비교

- **질문:** Zipf 쏠림을 split + 이동으로 고칠 때 정책별 분할의 질과 서비스 영향.
- **방법:** 4대. 러너가 자기가 보낸 key 분포로 TabletLoad를 만들고 SplitPolicy를 돌려 CONTROL로 split·move 지시. 정책 3개를 상태 리셋을 끼워 한 런에서 순차 실행(안 되면 3런).
- **비교 축:** midpoint / heat(θ0.6) / heat(θ0.8).
- **지표:** 분할 횟수, 효과 없는 분할, 최종 균형(노드별 요청 max/mean), 복구 중 p99, 정합성 3종.
- **주의 1:** 복구 "시간"은 관측 window 길이가 지배 — 같은 window 조건의 상대 비교로만 해석.
- **주의 2:** 이 단계는 복사 없는 cutover라 이동 때마다 새 주인에서 miss가 난다. **SET 위주 부하**로 miss 영향을 제거한다(GET 영향은 E4에서). cleanup 적용으로 반복 이동의 stale HIT를 막는다.
- **런 1~3.** 이 런의 cutover 구간이 E4의 "복사 없음 참고선"을 겸한다.

### E4. 이동 방식 — B3 복사 방식 비교

- **질문:** Tablet을 옮기는 동안 서비스가 어떻게 되나. 쓰기율에 따라 어느 방식이 좋은가(B3 시뮬레이션의 핵심 결론 검증).
- **방법:** 2~4대. GET 포함 부하(DELETE 30%)를 유지하며 뜨거운 Tablet 하나를 이동. **쓰기율 2단계(낮음/높음)를 한 런 안에서 순차** 실행.
- **비교 축:** stop-and-copy vs **pre-copy**. post-copy와 그 외는 시뮬레이션 인용. "복사 없음"은 B3 방식이 아니라 **참고선**(E3 런에서 확보).
- **rho 정의(실서버):** 이동 Tablet으로 들어오는 쓰기 bytes/s ÷ **iperf3 실측 이동 대역**. 조건마다 기록한다.
- **이동 Tablet 크기:** key 수·bytes를 조건으로 명시한다. 너무 작으면 복사가 순식간에 끝나 볼 것이 없다. 시뮬레이션과 bytes 기준으로 맞추거나 차이를 §7에 명시.
- **지표:** 이동 중 miss율·적중률 회복 곡선, p99 스파이크(open-loop), write 차단(freeze) 구간 길이, 이동 총시간·전송 bytes, **BUSY 비율·재시도 포함 지연**(post-copy 실행 시), 정합성 3종.
- **pre-copy 내부 기록(시뮬레이션과 동일 항목):** 라운드 수, 라운드별 dirty bytes, 종료 사유(임계/상한/NOT_SHRINKING), 마지막 freeze 동안 보낸 bytes.
- **가설(§7):** "pre-copy의 쓰기 차단은 Tablet 크기와 무관하게 짧다", "쓰기율이 높으면 pre-copy 전송량이 커진다".
- **런 2** (stop / pre-copy 각 1, 쓰기율은 런 내).

### E5+E6. 다중 이동 스케줄러 × scale-in (통합)

- **질문:** source를 공유하는 이동 여러 건에서 스케줄러 정책이 "전체·평균 완료 시간 vs 서비스 p99" 트레이드오프를 어떻게 바꾸나. scale-in drain은 끝까지 안전한가.
- **방법:** 4~8대. **scale-in drain으로 이동 묶음을 만든다**: 노드 하나를 빼기로 하고 그 노드의 Tablet 전부(= source 공유)를 다른 노드들로 이동. 잔여 Tablet 0 확인 후 제거(ScyllaDB decommission 규칙). 흩어진 이동 8건을 임의로 만들면 정책 간 차이가 거의 안 난다.
- **비교 축:** FIFO(기준) / MongoDB-style(노드당 동시 1개) / SLAMIG — 시간 부족 시 앞 2개. (정책 선정과 구성은 B3 담당 협의. 현재 scheduler 결과는 조건별 비교이며 단일 우승을 정하지 않는다 — [scheduler-comparison](../b3-live-migration/scheduler-comparison/results.md))
- **지표:** 전체 이동 완료 시간(makespan), **평균 job 완료 시간**, job별 쓰기 차단, 전송 배율, 이동 중 p99, 노드별 NIC 송수신량, drain 완료 시간, 잘못된 제거 0건, 정합성 3종.
- **가설(§7):** "source 공유 시 노드당 동시 1개 제한이 FIFO보다 완료 시간이 짧다".
- **구현 전제:** pre-copy wire(§5) 선행.
- **런 2~3** (정책당 1).

### 여유 시 추가 (각 1런)

- **scale-out:** 4대 운영 중 5번째 노드 join → B1 `onNodeAdded` 계획 → Scheduler 이동 → 균형 회복까지 p99·완료 시간.
- **source kill:** pre-copy 도중 source 프로세스를 kill → 원상태 복귀, 유실·이중 소유 0 확인 (시뮬레이션 S6은 in-process 취소였다).
- **post-copy:** BUSY 비율·재시도 포함 지연 측정. 미도착 key를 source가 대신 응답하는 보완 버전인지 여부를 명시하고 실행한다.

## 5. 선행 구현 작업

| # | 작업 | 담당 | 필요한 실험 |
|---|---|---|---|
| 1 | 배포가 B1ServerMain을 돌리는 모드 (user_data에서 노드별 config 생성) | B1 | 전부 |
| 2 | 러너 멀티노드 클라이언트 (§3 요구사항 전부: 직행·MOVED 추적·hop 태깅·BUSY 재시도·집계·CONTROL·정합성 oracle·상태 리셋) | **B1+B3 (협의 필요** — Runner 모듈 담당은 B3) | 전부 |
| 3 | 러너에 B2 SplitPolicy 탑재 (관측 → 결정 → CONTROL) | B1+B2 | E3 |
| 4 | 서버 B3 이동 wire | B3 (B1은 commit 연결) | E4~E6 |
| 5 | 서버 B3 스케줄러 연결 | B3 | E5 |

**4번의 범위 (freeze 훅만으로는 부족):**

- 공통: Tablet 단위 scan, 일괄 적재, 범위 삭제, `KeyHash` 기준 worker 선택, **cutover-only 경로의 commit 후 cleanup**(§1, E2·E3에도 필요)
- pre-copy: 쓰기 관찰 hook (dirty 추적)
- post-copy: destination → source pull 경로 (여유 시)
- commit: controller가 expected version/epoch를 확인하는 조건부 적용 — E5 동시 이동에서 commit 유실 방지 (B1 `Controller.move` CAS가 담당)

**실행 순서 (11/18 역산):**

1. 작업 1·2 → **E1·E2 실행** (wire 무관, 바로 가능) · 작업 3 → **E3**
2. stop-and-copy wire → pre-copy dirty hook → **E4**
3. 스케줄러 연결 → **E5+scale-in**
4. 여유 시: scale-out, SLAMIG, source kill, post-copy

## 6. 하지 않는 것

- B1 6방식의 실서버 재비교 — 표 만드는 규칙 차이라 네트워크에 올려도 균형·이동량이 같다. [시뮬레이션 결과](../b1-tablet-distribution/) 인용.
- B2 θ 전체 스윕 — [시뮬레이션](../b2-load-balancing/)으로 충분. 실서버는 대표 2개.
- B3 **노드 증감 판단 정책**(PAX, E-Store 등) 실서버 비교 — 판단 입력이 모형이라 실서버가 더해 주는 것이 없다. [시뮬레이션](../b3-live-migration/scaling-decision/results.md) 인용.
- B3 스케줄러 9개 전수·post-copy 기본 포함 — 대표만 실측, 나머지는 시뮬레이션 인용.
- 처리량 포화 측정 — 부하 생성기 1대 제한. 고정 RPS 지연 비교로 대체.

## 7. 시뮬레이션 → 실서버 검증 구조 (E4·E5 해석)

- 실측 대역으로 tick을 ms로 환산(1 tick = 64 KiB ÷ iperf3 실측 대역)해, 시뮬레이션이 예측한 freeze·완료 시간과 실측을 나란히 둔다.
- 실험별 검증 가설을 한 줄씩 명시한다(E4·E5 본문).
- 조건 차이를 결과에 명시한다: value 크기(시뮬레이션 128 B vs 실서버 1 KiB), 이동 Tablet 크기(bytes 기준으로 맞추거나 차이 기록), DELETE 30%는 동일.
- B3 수치 인용은 experiments/b3-live-migration/의 현재 결과 문서 기준. 요약 수치를 설계서에 복사하지 않고 링크한다.
