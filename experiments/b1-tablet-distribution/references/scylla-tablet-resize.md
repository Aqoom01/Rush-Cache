# ScyllaDB tablet resize: 전체를 2배 / 절반으로

B1-A(고정 슬롯)와 B1-B(해시 범위 Tablet) 사이의 변형 `resizable-slot`(B1-E)의 근거. 균등 슬롯을 유지하되 슬롯 수를 운영 중에 바꾼다. 단, 슬롯 하나씩이 아니라 **테이블 전체를 한꺼번에** 2배 또는 절반으로.

## 출처

- [ScyllaDB — Data Distribution with Tablets](https://docs.scylladb.com/manual/master/architecture/tablets.html): "Absolute number of tablets", "Tablet split and merge" 절
- ScyllaDB 블로그 "Tablets: Rethinking Replication" 계열 글(tablet 수가 2의 거듭제곱인 이유, split/merge를 쌍으로 하는 이유)
- 비교 대상: Google Slicer(OSDI 2016) §4.4의 slice별 split/merge → [slicer-scylla-tablets.md](slicer-scylla-tablets.md)

## 핵심 아이디어

ScyllaDB는 테이블마다 tablet 수를 **2의 거듭제곱**으로 두고, 토큰 범위를 그 수로 균등하게 나눈다. 데이터가 늘어 **평균 tablet 크기가 목표(`target_tablet_size`, 기본 5 GB)의 2배를 넘으면 모든 tablet을 동시에 반으로 쪼개고**(수 2배), 평균이 목표의 절반 아래로 내려가면 **이웃한 쌍을 합친다**(수 절반). 결정은 평균 하나로 하므로 어느 tablet이 뜨거운지는 보지 않는다.

```text
tablet 수 S = 2^k, 토큰 범위를 S 등분
                       평균 크기 > 2 × 목표          평균 크기 < 목표 / 2
[ 0 ][ 1 ][ 2 ][ 3 ]  ──────── split ────────▶  [0a][0b][1a][1b][2a][2b][3a][3b]
                      ◀─────── merge ─────────
```

- split은 메타데이터만 바뀐다. 쪼개진 두 조각은 부모와 같은 노드(복제 집합)에 있으므로 데이터가 움직이지 않는다.
- merge는 쌍이 **같은 복제 집합에 있어야** 한다. 노드 증감 뒤에는 쌍이 다른 노드에 있을 수 있어, 로드 밸런서가 먼저 한쪽을 옮겨 모은 뒤(co-locate) 합친다. 그래서 merge는 split보다 비싸고 두 단계다.
- 처음 tablet 수는 노드 수·샤드 수·목표 크기에서 계산한다(`tablets_per_shard_goal` 같은 설정으로 샤드당 개수를 맞춘다). 노드가 늘면 샤드당 tablet이 줄어드니 split 쪽으로, 줄면 merge 쪽으로 기운다.

고정 슬롯(B1-A)과의 차이는 **슬롯 수가 바뀐다**는 것, 해시 범위 Tablet(B1-B)과의 차이는 **하나씩이 아니라 전부 한꺼번에** 바뀌고 **균등 분할이 유지된다**는 것이다.

## 효과와 한계

얻는 것
- 노드 수·데이터 양에 맞춰 단위 수를 조절한다. B1-A는 슬롯 수가 영원히 고정이라 노드가 많아지면 노드당 슬롯이 너무 적어지고(정수 나눗셈 불균형), 적으면 표만 크다.
- 균등 분할이 유지되므로 B1-B처럼 Tablet 길이가 제각각이 되지 않고, 개수만 세면 균형을 안다. 표도 fixed-slot처럼 구간 압축이 된다(경계를 보낼 필요가 없다).
- 2배는 데이터 이동이 없다.

잃는 것
- **특정 Tablet만 쪼갤 수 없다.** 뜨거운 Tablet 하나 때문에 전체를 2배로 늘려야 하고, 표 크기(구간 수)와 조회 깊이가 함께 는다. 쏠림 대응은 B1-B(개별 split)가 세밀하다.
- **절반은 이동이 따른다.** 쌍이 다른 노드에 있으면 한쪽을 옮겨야 한다. 노드 증감을 거친 표에서는 쌍의 절반 가까이가 섞여 있을 수 있다.
- 결정이 평균 기준이라 쏠림을 보지 못한다. ScyllaDB도 쏠림은 split이 아니라 load balancer의 이동으로 푼다.

## 질문

1. 노드 수가 1 → 16 → 8로 움직이는 동안(S4) 슬롯 수는 몇 번, 언제 바뀌고 표 크기는 얼마나 되는가? fixed-slot(고정 4096)과 비교해 노드당 슬롯 수가 범위 안에 유지되는가?
2. 크게 줄였다 늘릴 때(16 → 2 → 16, S9) 절반(merge)에 드는 이동이 노드 증감 자체의 이동에 더해 얼마나 되는가? 이론 Σ 1/n 대비 몇 %인가?
3. 노드 8대에서는 fixed-slot과 같은 표인가(S1·S5·S7이 자리수까지 같은가)?

## 프로젝트 적용

- `core.tablet.resize.ResizableSlotScheme`. 슬롯 수는 2의 거듭제곱, 처음 표는 노드 수 × T(노드당 목표, 기본 512) 이상인 가장 작은 2의 거듭제곱. 노드당 슬롯 수가 T/2 아래면 2배, 2T 위면 절반(히스테리시스).
- 2배(`doubled`)는 모든 슬롯을 한가운데서 쪼갠다. 왼쪽은 id 유지, 오른쪽은 새 id(`RoutingTable.withSplit`과 같은 규칙). 노드 추가 때 필요하면 계획의 `prepared`로 먼저 적용된다(주인이 안 바뀌므로 `Plan`의 뜻에 맞는다).
- 절반은 두 단계: `halving`이 섞인 쌍을 한쪽으로 모으는 이동 계획을 주고(쌍마다 이동 1건, 그래도 노드 간 쌍 수 차이가 1을 넘으면 쌍 단위로 더 옮김), 이동이 끝나면 `merged`가 메타데이터만 바꿔 합친다. 노드 제거 계획 안에서는 하지 않는다(계획의 이동은 모두 떠나는 노드에서 나가야 한다는 불변식 6).
- ScyllaDB의 기준은 평균 tablet **크기**지만 우리는 데이터 크기를 모르므로 **노드당 슬롯 수**로 바꿨다. 같은 모양의 규칙(목표의 절반 / 2배)이다.
- 비교 실험: S4에 슬롯 수·표 크기 최대를 추가 기록, 새 시나리오 S9(16 → 2 → 16)에서 절반·2배 횟수와 그에 든 이동을 잰다. 결과는 `distribution-comparison/results.md` 5차.
