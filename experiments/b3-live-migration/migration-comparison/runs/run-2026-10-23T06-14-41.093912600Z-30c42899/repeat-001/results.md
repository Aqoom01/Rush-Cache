S1~S5의 16조건 × seed 5개 × 3방식, 총 240회. 정합성 위반 0건, destination 전체 비교 240/240건 일치.

동일 case/seed의 초기 데이터와 tick별 GET/SET/DELETE **시도**는 같다. BUSY인 쓰기는 적용하지 않는다. 실행 길이가 다르므로 각 방식이 소비한 요청열 길이·성공 쓰기 수는 다르다. inputHash는 generator·설정·seed의 규격 hash이며 실제 materialized trace hash가 아니다.

가상 tick·인메모리 모델이다. 전체 시간은 begin~cleanup 완료, 쓰기 차단은 누락 key DELETE 제어 요청의 BUSY tick 수다. 제어 요청은 데이터/dirty/workload에 영향을 주지 않는다. 단계/라운드 경계는 각 원본의 phaseEvents에 기록한다.

전송량은 직렬화된 데이터 응답 bytes다. snapshot 헤더 29, delta 헤더 30, post-copy key별 응답 헤더 33 bytes를 포함하고 ACK/pull 요청의 제어 bytes는 제외한다. 전송량 비율 분모는 이동 전 N×152 bytes다. 삭제로 줄어든 최종 크기도 JSON에 별도로 기록한다. post-copy의 미도착 GET은 BUSY이며 false MISS로 간주하지 않는다.

## 범위와 제한

균등 분포와 finite Zipf CDF(역변환, 고정 rank→key permutation)를 이 backend에서 구현했다. 공통 Workload Generator를 수정하지 않는다. 쓰기율 rho는 시도당 152 bytes 기준이며 DELETE의 tombstone 크기·같은 key 반복으로 실제 dirty 전송량과 같지 않다. 초기 값은 모두 같은 128-byte payload이고 이후 SET은 tick/연산 번호를 담는다. post-copy는 key manifest를 수집한 뒤 commit하며 이 준비/CAS의 실제 비용은 모델에서 측정하지 않는다.

S6의 취소·장애 경계는 기존 프로토콜 테스트로 별도 검증한다. 이번 suite는 S6 성능 비교·S3 임계/라운드 민감도·E/M scaling·실제 서버 실험을 포함하지 않는다. 기존 SC 결과와 이번 결과는 별도 schema이며 자동 합산하지 않는다.
