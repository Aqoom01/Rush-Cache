## 검증·해석 범위

총 1386개 job 모두 DONE·최종 데이터 exact match·이전 source 정리·owner/epoch 전환을 확인했다. 매 tick의 전체/노드별 할당·실소비·동시 상한 검증과 JSON 재검증에서 위반 0, 미시작 job 0이다. 대기 p99는 run 내부 job 시작 대기의 nearest-rank 분위수를 구한 뒤 seed 평균을 냈다. 처리량은 전송 bytes/전체 완료 tick이다.

M1~M3는 Stop-copy, M4는 dirty 변화가 드러나는 Pre-copy를 기준으로 삼았다. M5가 M2/M4의 같은 조건을 세 방식 모두로 반복한다. rho는 job당 고정 reference bytes/tick으로 생성한 쓰기 시도량이며 실제 할당량으로 낮추지 않는다. SET 70%·DELETE 30%, job/tick마다 GET 2개를 시도한다. 대기/완료한 job에도 suite 종료까지 같은 생성 규격을 적용한다. BUSY와 완료 시각 때문에 성공 요청·최종 데이터량은 방식마다 다르며 각자의 성공 요청 oracle로 비교했다. workloadHash는 전체 trace 파일이 아닌 생성 규격의 hash다.

FIFO는 실행 가능한 가장 오래된 job을 고른다. 공유 endpoint는 송수신 합산 예산, 전체 예산은 전송 1 byte당 한 번 차감한다. 회전 progressive filling으로 나누고 미사용 예산은 같은 tick에 재분배하거나 다음 tick으로 이월하지 않는다. ACK/control/실제 network framing은 기존 protocol byte 모델 밖이다. queued starvation=0은 이번 유한 입력의 관측이며 지속 도착·장애 환경의 보장이 아니다.
