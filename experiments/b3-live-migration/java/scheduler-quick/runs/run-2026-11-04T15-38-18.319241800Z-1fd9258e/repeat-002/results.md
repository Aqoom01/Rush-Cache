## 검증·지표 범위

총 3888개 job의 exact match·단일 소유권/epoch 전환·source 정리·같은 source의 guard 보존을 실행 시 검증했다. JSON에서 job lifecycle·전송 bytes·매 tick 전체/노드 예산·동시 상한·TiDB 변형의 token 소비·최종 phase·집계를 다시 검증했다. 위반 0, 모든 job DONE이다.

동일 scenario/seed의 초기 데이터·외부 요청 생성 규격·후보 계획 hash를 모든 방법/복사 방식에 공통 적용했다. 성공 요청 및 종료 시각은 방식마다 다르므로 각자의 성공 요청 oracle로 비교한다. 쓰기율을 실제 배분 예산에 맞춰 낮추지 않는다. Post-copy의 freeze/commit은 같은 controller step이어서 write 차단 tick이 0일 수 있고, 실제 downtime 0이라는 뜻은 아니다. 전송 bytes는 protocol payload/header 기준이며 ACK/control/TCP·SSD 비용은 제외한다.

대기 p99는 run 내부 12 job 시작 대기의 nearest-rank 분위수 후 seed 평균이다. 평균 job 완료 시간은 입력 시각 0부터 각 DONE까지의 평균이다. deadline scenario의 기한만 유효하며 나머지는 10000 tick의 비긴급 조건이다. plannerWallNanos는 fixture 적재를 제외한 한 JVM 안의 관측으로 warm-up/하드웨어가 통제된 CPU 벤치마크가 아니다. timings.csv에 보존하되 결정적 summary/results 및 evidenceHash에는 포함하지 않는다.

정식 진입점은 공통 Runner config이다. JSON `results/*.json`이 원본이며 jobs.csv/budgets.csv/rounds.csv/paired.csv/timings.csv는 파생 자료다. Git에는 정식 반복의 summary.csv/results.md만 보관하고 원본·상세 자료·manifest는 로컬에 남긴다.

job별 generation 관측은 [dirty 상세](dirty-rounds.md)와 [이벤트 CSV](dirty-rounds.csv)를 따른다. rounds.csv는 기존 단계 기록으로 유지한다.
