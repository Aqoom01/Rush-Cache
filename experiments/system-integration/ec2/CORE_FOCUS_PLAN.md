# EC2 핵심 통합 실험 — 24시간 예산

2026-11-13. 본실험은 EC2에서 수행한다. 로컬36회는 예비 자료로 보존하며 EC2 순위 선정에 합치지 않는다. [이전 로컬 계획](LOCAL_CORE_FOCUS_PLAN.md)은 별도로 보존했다. 이 문서는 실행 계획이며 EC2 실행 완료 기록이 아니다.

## 실행 조건

전용 replica host6대 + gateway1대 + load1대, 그룹2개×replica3개를 사용한다. 한 번에 한 실험만 순차 실행한다. 실제 host 확보·접속·포트 확인·배포가 필요하다. 준비된 그룹을1↔2로 논리 증감하며 물리 EC2 생성·삭제 시간은 비교하지 않는다. 모든 실행에 A1 승인/소유권 + A2 데이터 엔진, A3 및 B파트를 함께 사용한다.

EC2 기준선에서 중간/과부하를 먼저 보정한다. 로컬의300/1000req/s를 EC2의 적정 부하라고 가정하지 않는다. 키·값·요청 tape·읽기 비율·다른 축을 고정하고 순서를 섞는다. 정상 비교는 읽기80%, 장애 비교는 읽기100%를 기본으로 한다.

순수 실행 약8~12시간, 준비·부하 보정·분석·선별 재실행을 포함해12~18시간을 목표로 한다. 나머지는 문제 대응·추가 반복 예산이다. EC2에서 아직 실측하지 않았으며 초기10회 wall time으로 예상 시간을 갱신한다. host가 확보되고 정상 접근 가능한 상태를 전제로 하며24시간 완료 보장은 아니다.

1차63회는 선별용1회다. 작은 차이나 후보 경계는 재실행하고, 최종 후보는 새 seed3개로 더 길게 측정한다. 확대 작업 집합에서 순위가 다르면 후보를 다시 검토한다. 준비·prefill·워밍업·정합성 audit·cleanup·원격 수집을 wall time에 포함한다.

## 비교·판정 범위

- B1/B2는 ORDER의 무분할/MIDPOINT/HEAT, GREEDY/SLICER와 RANGE·RING_ALLOC의 호환 설정을 중심으로 한다. 같은 ordered-key 부하로 실제 분할·이동을 확인한다. Ring은 소유권 제약이 있어 허용되는 전체 설정으로 비교한다.
- A3는 F3, REDIS_CLUSTER, PHI_GOSSIP, IGNITE_TCP_RING, AEROSPIKE_MESH다. 기본 설정을 보존하고, 느린 FD를 현재1초 고정 pause로 평가하지 않는다. Ignite 고정 coordinator 장애 등 미지원 조건은 제외/UNSUPPORTED로 기록한다.
- 자동 증감 정책·scheduler 전체 순위는 이번 핵심 범위에서 제외한다. B3는 증감 시 실제 복사·이동 방식을 우선 비교한다. 학습·모델 자료 없이 TRAINING을 정책 성공으로 세지 않는다.
- 성공 처리량·p99·미수락/실패·FD 오판정·서비스 재개·이동 시간/bytes·CPU/RSS·정합성을 함께 본다. 정합성 실패를 빠른 승자로 선정하지 않는다.
- 호스트 간 monotonic 시각을 직접 빼지 않는다. 장애 주입·상태 관측은 controller 공통 시계의 관측 구간, 클라이언트 지연·실패 구간은 client 시계로 계산한다. 필요한 controller timestamp 보강을 실행 전에 한다.
- 현재 파일 저장소·OS page cache·fsync=false 등 prototype 범위를 유지한다. EC2 결과를 원제품 전체나 SSD 하드웨어 성능 검증으로 주장하지 않는다.

실행은 [HEADLESS_EXECUTION.md](HEADLESS_EXECUTION.md)의 `EXPERIMENT_SUITE=integrated-core` 경로를 사용한다. 서버가 pilot4회에서 부하를 보정하고 위155회의 후보 선정·입력 생성·실행·S3 검증·EC2 정리를 자동으로 이어간다. 현재 run_core_focus.py와 core_followups.py는 과거 로컬 전용이므로 그대로 실행하지 않는다. 실제 계정의1행 preflight 확인은 아직 필요하다.

결과는 측정한 부하에서 유리한 통합 조합·순위가 바뀐 조건·근거로 보고한다. 전체 Cartesian이나 모든 고차 상호작용의 절대 최적은 주장하지 않는다. cleanup이 불완전하면 다음 실행을 멈춘다.
